# Design

## Context

参见 `proposal.md` 的动机和 `specs/profile-avatar/spec.md` 的行为契约。当前头像由 `getAvatarPresentation` 根据昵称或账号生成，`Profile.vue` 与 `BasicLayout.vue` 分别消费；`/api/auth/profile` 和 `/api/auth/me` 均不返回头像字段，`sys_user` 也没有头像列。

项目已有本地磁盘文件服务，但上传接口要求 `system:file:add`、接受通用文件，并将文件纳入管理员文件列表与删除流程，不能直接作为普通用户头像入口。JWT 由前端放入请求头，浏览器原生 `<img>` 请求无法自动携带该请求头，因此头像读取也不能复用受保护下载接口。现有建表脚本以 `CREATE TABLE IF NOT EXISTS` 为主，新增列必须显式兼容已经存在的 H2 文件库。

## Goals / Non-Goals

**Goals:**

- 让任何已登录用户只维护自己的头像，不授予通用文件管理权限。
- 在浏览器中提供可触控的方形裁剪体验，同时由服务端执行可信校验和规范化。
- 让头像替换具有唯一资源地址，避免浏览器缓存继续展示旧图片。
- 将数据库关联更新、失败回滚与旧文件清理收敛到专用头像服务。
- 保持现有空头像用户、登录会话和字符头像回退逻辑兼容。

**Non-Goals:**

- 不提供头像图库、摄像头拍摄、旋转、滤镜或多尺寸人工管理。
- 不允许管理员在本变更中代用户上传头像，也不改造系统用户管理页面。
- 不把头像加入通用文件列表，不改变通用文件模块的权限和删除语义。
- 不引入对象存储、CDN、病毒扫描服务或异步图片处理队列。

## Decisions

### 1. 用户表保存头像资源键，DTO 对外返回资源 URL

在 `sys_user` 增加可空 `avatar` 列，值仅为服务端生成的 UUID 文件名，而不是用户提供的路径或完整部署域名。`SysUser`、`LoginUser`、`SysUserVO`、`ProfileVO` 与 `UserInfoVO` 扩展头像字段；对外 DTO 将资源键转换为 `/api/profile-avatars/{key}` 形式的 `avatarUrl`。

资源键与部署地址解耦，也让删除操作只能落在受控头像目录。头像为空时 DTO 返回空值，由前端继续调用现有字符头像规则。JWT 过滤器每次请求都会重新加载 `LoginUser`，因此用户更新头像后的下一次 `/me` 请求可以读取最新头像，无需重签 Token。

备选方案是将完整 URL 写入用户表，但它会把域名、上下文路径和部署拓扑固化进业务数据；将图片二进制或 Base64 写入用户表则会放大常规用户查询和备份体积，均不采用。

### 2. 写接口登录保护，读接口使用不可预测键公开只读

认证模块新增：

- `POST /api/auth/avatar`：接收 multipart 字段 `file`，从安全上下文确定用户，返回新的 `avatarUrl`。
- `DELETE /api/auth/avatar`：移除当前用户头像，无用户 ID 参数。
- `GET /api/profile-avatars/{key}`：仅按严格 UUID PNG 文件名读取头像内容。

前两个接口受现有 `anyRequest().authenticated()` 保护且不增加业务权限注解。只读资源接口允许匿名访问，以便 `<img>` 正常加载；资源键为服务端随机 UUID、接口不提供目录浏览或按用户查询，并设置 `X-Content-Type-Options: nosniff` 与固定 `image/png` 响应类型。

成功生成的新头像使用新键，并返回 `Cache-Control: public, max-age=31536000, immutable`。替换头像不会复用 URL，因此无需客户端拼接时间戳或禁用缓存。

备选方案是前端通过带鉴权的 HTTP 客户端获取 Blob 再生成对象 URL，但这会让个人中心和全局布局重复管理加载、回收与刷新状态，并使页面刷新后的头像展示更复杂，因此不采用。

### 3. 前端负责交互裁剪，服务端负责可信图片处理

前端增加 `cropperjs` 2.x，直接封装为项目内 Vue 组件，不引入额外 Vue 包装层。用户选择文件时先校验扩展名、浏览器 MIME 和 5 MiB 上限，再通过对象 URL 打开模态裁剪器；裁剪区域固定为 1:1，支持拖动与缩放，并导出 512×512 的 PNG Blob。关闭或更换文件时及时撤销对象 URL。

服务端仍将上传视为不可信输入：先执行 5 MiB 硬限制，再通过 ImageIO reader 识别实际 JPEG/PNG 格式并读取尺寸；拒绝不可解码图片以及宽或高超过 4096 像素的输入。通过校验后按居中覆盖规则规范化为 512×512 PNG，重新编码以去除原始元数据。文件名完全由服务端生成，存放于 `${admin.upload.path}/avatars`。

前端裁剪改善体验，服务端规范化则防止绕过客户端、伪造 MIME、路径注入和超大像素图片消耗资源。只依赖客户端裁剪缺少安全边界；只由服务端自动居中裁剪又无法让用户选择头像构图，均不采用。

### 4. 新文件先落盘并更新关联，旧文件在提交后清理

上传替换按以下顺序执行：

1. 校验并将规范化图片写入同目录临时文件，再原子移动为新的 UUID 文件。
2. 在数据库事务中以用户 ID 与旧头像键作为比较条件，将当前用户的 `avatar` 从旧键更新为新键；并发请求若已改变头像则本次写入失败并清理新文件。
3. 数据库提交成功后删除旧键对应文件；数据库更新失败则删除本次新文件并保留旧关联。

移除头像同样以用户 ID 与旧头像键进行条件更新，清空关联提交成功后才删除旧文件。`SysUser.avatar` 禁止被通用实体更新语句写入，只允许头像服务显式维护，避免资料或密码更新把过期头像键写回。旧文件删除失败不回滚已经成功的用户状态，而是记录包含资源键的告警，供运维清理；后续可增加孤立文件巡检，但不扩大本次范围。所有路径都以生成的 UUID 文件名和固定头像根目录解析，并校验规范化路径仍位于该目录内。

文件系统和数据库不具备共同事务，无法保证物理清理与关联更新绝对原子。优先保证用户不会指向半成品或不存在的新文件，接受极少量旧文件在异常删除时成为可观测的孤立资源。

### 5. 头像状态独立于基本资料表单

个人中心在现有 72px 头像附近提供带相机图标的编辑操作，打开裁剪模态框；已有自定义头像时额外提供带确认对话框的移除操作。上传状态只锁定头像相关控件，不改变 `profileForm`、资料基线或未保存离开判断。

上传成功后先使用响应中的 `avatarUrl` 更新个人中心，再调用 `auth.refreshUserInfo()` 更新顶部导航；移除成功同理切回生成头像。若全局刷新失败，保留服务端已确认的新状态并提示同步失败，后续路由刷新会恢复。`getAvatarPresentation` 扩展为同时返回图片 URL 和原有字符回退数据，两个消费者统一在图片 `error` 事件后显示回退内容。

头像操作在窄屏保持可触达，图标按钮提供 tooltip 与可访问名称；裁剪容器使用稳定宽高约束，不能因加载图片或上传状态造成布局位移。

### 6. 使用显式幂等迁移兼容已有数据库

在建表脚本中除更新 `sys_user` 定义外，增加适用于当前 H2/MySQL 模式的幂等 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS avatar VARCHAR(255)`，确保已有本地数据库获得新列。种子数据、用户导入和既有创建接口可以不传头像，默认保持 `NULL`。

部署顺序为后端与数据库兼容变更先行，再发布引用 `avatarUrl` 的前端。旧前端会忽略新增响应字段；新前端在字段为空时保持原行为，因此滚动发布兼容。

## Risks / Trade-offs

- [公开只读头像 URL 可被获得链接的人访问] -> 使用不可预测 UUID、不暴露目录与用户映射，且头像本身按公开身份图片处理；若未来头像需要访问控制，应改为带签名的短期 URL。
- [恶意压缩图片可能消耗解码资源] -> 同时限制上传字节数与像素尺寸，在完整解码前通过 reader 获取尺寸，并在请求线程内只生成单一固定尺寸。
- [数据库提交后旧文件删除失败会遗留孤立文件] -> 记录资源键和明确告警，不让清理失败破坏用户当前头像；后续可通过运维脚本按用户表引用集合清理。
- [Cropper.js 增加前端包体积] -> 仅在个人中心异步加载裁剪组件，避免进入通用布局首屏包。
- [透明 PNG 规范化后的文件可能大于 JPEG] -> 头像尺寸固定为 512×512，体积上界可控，并保留透明背景以避免不可预期的底色。

## Migration Plan

1. 先应用幂等用户表列迁移并部署后端头像存储、读写接口；确认空头像用户的现有登录和资料接口兼容。
2. 部署前端裁剪与头像展示逻辑，使用无头像、首次上传、替换、移除和非法图片场景验收。
3. 观察头像处理错误、旧文件删除告警和磁盘增长情况，并确认公开资源响应头与缓存行为。
4. 如需回滚，先回滚前端再回滚后端代码；保留可空数据库列和头像目录，避免破坏已产生的数据。重新发布后端即可恢复已有自定义头像。
