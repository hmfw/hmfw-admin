# Design

## Context

参见 `proposal.md` 的动机。当前个人中心的展示、资料编辑和密码修改全部位于 `Profile.vue`，调用现有 `getProfile`、`updateProfile`、`updatePassword` 与 `auth.refreshUserInfo`；顶部导航则在 `BasicLayout.vue` 中用统一用户图标和已有显示名称呈现当前用户。组件库已提供 Tabs、Skeleton、Alert、Modal、Form 等所需组件，路由层支持组件内离开守卫，因此无需新增依赖或修改后端。

页面位于全局白色 Content 容器内；设计需避免继续嵌套多层卡片，同时沿用项目现有的主色、圆角、间距和 `760px` 左右的移动端断点习惯。

## Goals / Non-Goals

**Goals:**

- 用稳定的信息层级组织身份摘要、基本资料和账号安全操作。
- 用一套可推导的页面状态处理加载、失败、资料变更、提交和离开保护。
- 保持现有 API 契约与全局用户状态同步方式。
- 使关键交互可通过组件测试验证，并在桌面端和窄屏下保持可用。

**Non-Goals:**

- 不引入头像上传、图片裁剪或文件生命周期管理。
- 不展示或编辑部门、角色、账号状态等管理员维护的信息。
- 不改变密码强度策略、Token 或其他登录会话的失效行为。
- 不将个人中心拆成新的路由层级或增加后端接口。

## Decisions

### 1. 使用身份摘要栏与受控页签工作区

页面顶部保留简洁标题和说明，主体使用两列 Grid：左侧约 `260px` 的身份摘要，右侧为自适应设置工作区。工作区使用线条式 Tabs 分隔“基本资料”和“账号安全”，默认激活基本资料。窄屏时 Grid 改为单列，身份摘要在前，主要提交按钮占满可用宽度。

身份摘要与工作区使用间距和分隔线建立层级，不再将每个区块包装为独立卡片。这样与外层 Content 容器一致，也避免卡片嵌套。

备选方案是继续纵向排列三个卡片，实现改动较小，但无法改善页面过窄、职责混杂和移动端信息密度问题，因此不采用。

### 2. 生成头像而不是复用文件上传

新增无状态头像展示工具，统一计算显示名称、头像字符和背景色。显示名称按 `trim(nickname) || username` 计算，头像取展示名称 `trim()` 后的首个字符并转为大写；异常空值回退为用户图标。背景色通过显示名称的稳定哈希映射到一组低饱和度色板，使同一用户在个人中心和 `BasicLayout.vue` 顶部导航中保持一致。工具函数独立测试，两个消费者不重复实现规则。

备选方案是复用文件管理上传接口，但该接口要求 `system:file:add` 权限，用户实体也没有头像字段，会把纯前端重构扩大为数据模型、权限和文件清理改造，因此不采用。

### 3. 用标准化快照统一驱动资料脏状态

资料加载成功后，将 `nickname`、`email`、`phone` 标准化为字符串，分别写入可编辑表单与不可变基线快照。`isProfileDirty` 对三个字段逐项比较；保存按钮仅在资料已加载、存在变更、表单未提交时可用。

保存成功后先用当前表单更新基线，再调用 `auth.refreshUserInfo()` 同步顶部导航。若刷新全局信息失败，资料保存结果仍视为成功，但保留统一错误反馈，用户下次加载可恢复一致状态。

备选方案是依赖表单组件内部的 touched 状态，但 touched 不能识别“修改后又恢复原值”，也无法稳定支持路由离开保护，因此不采用。

### 4. 显式建模资料加载状态

页面使用 `profileLoading`、`profileLoadError` 和已加载资料三种互斥呈现：加载时显示带头像与表单轮廓的 Skeleton；失败时显示内联 Alert 和“重新加载”按钮；成功后才渲染身份摘要及可提交表单。重新加载复用同一加载函数，并在发起请求时清空旧错误。

这避免请求期间短暂显示空白可编辑表单，也让失败恢复路径可见。全局请求层仍负责通用错误消息，页面状态负责提供原地重试。

### 5. 用受控导航处理未保存修改

Tabs 使用受控 `activeTab`。用户从基本资料切换到账号安全时，若 `isProfileDirty` 为真，则通过确认对话框决定是否切换；确认放弃时先从基线恢复表单，再更新页签。

应用内离开由 `onBeforeRouteLeave` 返回 Promise：无未保存修改时直接放行，有修改时由同一确认逻辑解析为放行或取消。浏览器刷新和关闭不增加 `beforeunload`，因为规格只要求应用内导航保护，且浏览器级提示不可定制、会对轻量资料表单造成额外干扰。

### 6. 两个表单独立提交并锁定输入

资料表单与密码表单保持独立的引用、规则和提交状态。提交期间禁用对应表单输入和按钮，避免重复请求；另一个页签的状态不受影响。

资料规则在前端对齐后端约束：昵称最多 50 字符、邮箱格式正确且最多 100 字符、手机号最多 20 字符。密码沿用原密码必填、新密码至少 6 位、确认密码一致的现有规则。密码修改成功后清空三项敏感字段并清除校验状态；失败时保留页面，但原密码是否保留遵循现有交互，避免引入接口语义变化。

### 7. 通过页面组件测试覆盖状态与交互

新增头像工具测试和 `Profile.spec.ts`，使用 Vue Test Utils 和 Vitest mock 鉴权 API、全局用户刷新与确认交互。测试重点包括：头像规则及两处展示一致性、昵称与账号回退、加载失败重试、未修改时禁用保存、有效保存后的基线与全局状态同步、未保存页签切换保护、密码一致性与成功清空。响应式行为通过稳定的结构类和 CSS 媒体规则断言补充人工视口检查。

不新增端到端测试框架；现有仓库只配置了 Vitest/jsdom，引入浏览器测试依赖超出本次范围。

## Risks / Trade-offs

- [生成头像无法表达用户真实形象] -> 明确将头像作为身份提示而非可维护资料，后续若有真实业务需求再设计专用头像能力。
- [保存成功但刷新全局用户信息失败会短暂不一致] -> 先更新本页基线和摘要，保留错误反馈；后续导航或重新登录会重新获取全局信息。
- [确认对话框与异步路由守卫组合可能产生重复导航] -> 所有未保存确认收敛为返回 Promise 的单一函数，并在提交期间禁止页签切换。
- [组件测试难以证明所有真实视口下的视觉效果] -> 使用明确的 Grid 约束、断点和无横向溢出规则，并在实现验收时补充桌面与移动视口检查。

## Migration Plan

1. 先补充页面组件测试并确认现有 API mock 契约。
2. 在原 `/profile` 路由内替换页面结构和状态逻辑，并让顶部导航复用共享头像展示规则，不迁移路由或数据。
3. 运行前端测试与生产构建，并在桌面和移动宽度检查布局及交互。
4. 若发布后需回滚，仅恢复前端页面、布局头像和共享工具相关改动；后端和持久化层没有迁移项。
